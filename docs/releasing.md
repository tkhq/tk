# Releasing `tk`

Pushing a `v*` tag runs the `release` workflow, which builds native binaries
for every supported target, checksums them, and publishes a GitHub release that
`install.sh` picks up.

```sh
git switch main && git pull --ff-only
git tag v0.2.0
git push origin v0.2.0
```

## Rules

- **The tag must point at a commit already on `main`.** The `validate` job
  refuses a tagged commit that is not an ancestor of `origin/main`.
- **Wait for `main` CI to pass on the commit before tagging it.** The release
  workflow builds but does not run the test suite.
- **Never move or reuse a published tag.** Bump to a new version instead; the
  installer resolves versions by tag name.

## The tag is the version

The manifest version in `Cargo.toml` stays at `0.1.0` and is never bumped:
nothing publishes to crates.io. The workflow passes the tag to the build as
`TK_RELEASE_VERSION`, and `tk/build.rs` bakes it into the binary as
`TK_VERSION`, which `tk --version` reports. Local builds fall back to
`git describe --tags`, then to the manifest version.

Release notes are generated by GitHub from the merged pull requests since the
previous tag. Revisit this when `tk` is published to crates.io: the manifest
version then has to match the tag, and `cargo-release` or `release-plz` is the
right tool.

## Artifact contract

Every release publishes, for each target:

```
tk-<target>-<vX.Y.Z>.tar.gz          # one directory, tk-<target>-<vX.Y.Z>/, holding tk and README.md
tk-<target>-<vX.Y.Z>.tar.gz.sha256   # `shasum -a 256` output (hash and filename)
```

Targets are built on native runners, without cross-compilation:

| target                      | runner            |
| --------------------------- | ----------------- |
| `x86_64-unknown-linux-gnu`  | `ubuntu-22.04`    |
| `aarch64-unknown-linux-gnu` | `ubuntu-22.04-arm`|
| `aarch64-apple-darwin`      | `macos-latest`    |
| `x86_64-apple-darwin`       | `macos-15-intel`  |

`install.sh` depends on this layout: it resolves the latest tag from the
`/releases/latest` redirect, downloads the archive and its checksum, requires
the checksum file to name that exact archive, inspects the archive listing
before extracting only the binary, smoke-tests it, and moves it into place
atomically. Change the naming scheme and the installer together. GitHub is the
trust boundary; artifact signing can be layered on later.

`tk/tests/release_pipeline.rs` asserts in `cargo test` that the tag must be on
`main`, every action is pinned to a commit, caches are read-only, and the build
matrix, installer, and release job agree on the target set.
